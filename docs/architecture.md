# Architecture

Pinpoint Feedback is a set of small packages. Each layer depends only on the layers below it, and every moving part sits behind an interface declared in `@pinpoint-feedback/core` ([`packages/core/src/interfaces.ts`](../packages/core/src/interfaces.ts)). The published `pinpoint-feedback` package only re-exports them.

## Packages

| Package | Contents | Depends on |
| --- | --- | --- |
| `@pinpoint-feedback/core` | Types, validation, limits, categories, i18n catalogs and locale bundles, DOM and display-media capturers, annotation editor, HTTP transport, outbox, client | `modern-screenshot` |
| `@pinpoint-feedback/react` | `FeedbackProvider`, `FeedbackWidget`, `useFeedback` (Shadow DOM UI, Tailwind-built CSS) | core; peer `react`, `react-dom` |
| `@pinpoint-feedback/server` | `createFeedbackRequestHandler`, `NotionFeedbackBackend`, `NotionFileUploader`, rate limiter, Notion schema/page builders | core, `@notionhq/client` |
| `@pinpoint-feedback/nextjs` | Client entry: widget with Next defaults. `./server`: `createFeedbackHandler`, `createFeedbackRouteHandlers` | core, react, server, `server-only`; peer `next` |
| `pinpoint-feedback` | Re-export files generated by `scripts/build.mjs` | all of the above |

All entries are ES modules only.

## Server/client boundary

- **No server code in client entries.** `core`, `react` and the `nextjs` client entry never import `@pinpoint-feedback/server`, `@notionhq/client` or `server-only`. The Notion SDK and the token are reachable only through `pinpoint-feedback/server` and `pinpoint-feedback/nextjs/server`.
- **`server-only`.** The Next.js server entry starts with `import "server-only"`, so importing it from a Client Component fails the build. `packages/nextjs/test/build.test.ts` checks the built output: the import comes first, the client entry has the `"use client"` banner and no reference to server code, and neither entry bundles `@notionhq/client`.
- **`"use client"` banners.** Vite adds the directive at build time: to every chunk of `react` (`output.banner`), and only to the `index` entry chunk of `nextjs`. Source files don't carry it.
- **No `export *` across a client boundary.** Next.js requires the directive in the module a Server Component imports, and rejects `export *` inside client modules. The umbrella build therefore reads the export names of the built `react` and `nextjs` packages (following `export *` chains) and writes explicit `export { … } from` lists into `dist/react.js` and `dist/nextjs.js`, each starting with `"use client"`. Server, core and locale entries use plain `export *`. Type declarations (`.d.ts`) always use `export *`.
- **Shared config from the root entry.** Category lists and locale bundles are plain data. Declare them in a module that imports from `pinpoint-feedback` (no client boundary), so a Server Component layout can pass them to the widget as props and the route handler can import the same values. Importing `defineCategories` from `pinpoint-feedback/nextjs` would give the server a client reference instead of a function.

## Interfaces

All exported from `@pinpoint-feedback/core`.

| Interface | Role | Implementations | Swap via |
| --- | --- | --- | --- |
| `ScreenshotCapturer` | Capture the current page into a `CapturedScreenshot` (PNG blob, size, scale, viewport, scroll, `warnings`) | `DomScreenshotCapturer` (default, `createDefaultCapturer()`), `DisplayMediaScreenshotCapturer` | widget `capturer` prop |
| `AnnotationRenderer` | Draw annotations on a 2D context, on screen and in the export | `defaultAnnotationRenderer` (`renderAnnotations`) | `createAnnotationEditor({ renderer })` |
| `FeedbackTransport` | Send one submission; returns a `SubmissionResult`, never throws for expected failures | `HttpFeedbackTransport` (multipart `POST`) | `createFeedbackClient({ transport })` |
| `FeedbackOutbox` | Durable client-side queue of unconfirmed submissions | `FallbackOutbox` via `createOutbox()` (IndexedDB, switching to memory if IndexedDB is unavailable or fails), `IndexedDbOutbox`, `MemoryOutbox` | `createFeedbackClient({ outbox })` |
| `MetadataCollector` | Collect `BrowserMetadata` (URL, title, browser, OS, viewport, screen, DPR, language, timezone) | `BrowserMetadataCollector` (`collectBrowserMetadata()`) | widget `metadata` prop (a `() => BrowserMetadata` function) |
| `FeedbackBackend` | Persist a validated submission; optional `findBySubmissionId` for idempotency | `NotionFeedbackBackend` | handler `backend` option |
| `FileUploader` | Upload one image, return a backend reference | `NotionFileUploader` (Notion File Upload API, single-part) | `NotionBackendOptions.uploader` |

`FeedbackClient` (`createFeedbackClient()`) composes a transport and an outbox; the widget takes a whole client through its `client` prop. Detailed contracts: capturers in [screenshots](screenshots.md), renderer in [annotation](annotation.md), client/outbox/backend idempotency in [reliability](reliability.md), backend and uploader in [notion](notion.md).

## Data flow

1. **Open.** The widget lives in an open Shadow DOM on a host marked `data-pinpoint-ignore`. On open it asks the `ScreenshotCapturer` for a `CapturedScreenshot`; elements with that attribute are always excluded. Content that can't be captured is replaced by a placeholder and reported as a `CaptureWarning`. If DOM capture fails, the dialog can offer `getDisplayMedia` instead.
2. **Annotate.** `createAnnotationEditor()` draws the screenshot and annotations on a canvas. Annotations are `Annotation[]` in screenshot pixel space. `exportAnnotated()` renders them onto a full-resolution copy.
3. **Submit.** `FeedbackClient.submit()` validates the payload, writes `{ submission, files }` to the outbox, then sends it through the transport: `multipart/form-data` with a `payload` JSON field and `screenshot` / `annotatedScreenshot` files. Retryable failures are retried with backoff. The entry is removed only when the server returns `{ ok: true }` (or a failure that can never succeed).
4. **Handle.** `createFeedbackRequestHandler()` checks method and origin, rate limit, content type and body size, the JSON schema (including the configured categories), honeypot and fill time, and the image magic bytes. It then deduplicates by `submissionId` (in-process cache, in-flight map, `findBySubmissionId`) and calls `FeedbackBackend.createRecord()`.
5. **Persist.** `NotionFeedbackBackend` resolves the database's first data source, adds missing properties and select options (`autoSetupSchema`), looks for an existing page with the same `Submission ID`, uploads both images through the `FileUploader`, and creates the page with properties and body blocks. Notion calls are throttled and retried.
6. **Confirm.** The handler answers `{ ok: true, submissionId, pageId, pageUrl, duplicate }`. The widget shows success only then; otherwise it keeps the draft and offers a retry. Pending outbox entries are resent on load and on the `online` event.

## Locale entry points

Built-in bundles are `packages/core/src/locales/<tag>.ts`, each with a named and a default export. The build turns every file there into a separate entry point:

1. `packages/core/vite.config.ts` reads `src/locales/` and adds one library entry per file. Output: `dist/locales/<tag>.js`, with shared code split into `dist/chunks/`. `package.json` exports them as `@pinpoint-feedback/core/locales/*`.
2. `packages/pinpoint-feedback/scripts/build.mjs` lists `core/dist/locales/*.js` and writes `dist/locales/<tag>.js` and `.d.ts` re-exports (`export *` plus `default`), exported as `pinpoint-feedback/locales/*`.

A new language needs no build change: add the file and rebuild. Importing one language doesn't pull in the others or the rest of core. Message catalogs, negotiation and RTL are covered in [i18n](i18n.md).
