# Internationalization

The widget, the annotation editor's screen-reader announcements, the placeholder labels drawn into screenshots, capture warnings and the Notion page body can all be localized. English is built in and used by default.

## Built-in languages

| Language | Tag | Import | Named export | Direction |
| --- | --- | --- | --- | --- |
| English | `en` | `pinpoint-feedback/locales/en` | `en` | ltr |
| German | `de` | `pinpoint-feedback/locales/de` | `de` | ltr |
| French | `fr` | `pinpoint-feedback/locales/fr` | `fr` | ltr |
| Spanish | `es` | `pinpoint-feedback/locales/es` | `es` | ltr |
| Italian | `it` | `pinpoint-feedback/locales/it` | `it` | ltr |
| Portuguese (Brazil) | `pt-BR` | `pinpoint-feedback/locales/pt-BR` | `ptBR` | ltr |
| Dutch | `nl` | `pinpoint-feedback/locales/nl` | `nl` | ltr |
| Polish | `pl` | `pinpoint-feedback/locales/pl` | `pl` | ltr |
| Japanese | `ja` | `pinpoint-feedback/locales/ja` | `ja` | ltr |
| Chinese (Simplified) | `zh-CN` | `pinpoint-feedback/locales/zh-CN` | `zhCN` | ltr |
| Arabic | `ar` | `pinpoint-feedback/locales/ar` | `ar` | rtl |

Each module exports the bundle both as the default export and under its camel-cased tag:

```ts
import de from "pinpoint-feedback/locales/de";
import { ptBR } from "pinpoint-feedback/locales/pt-BR";
```

Each language is its own entry point, so only the languages you import are bundled. A bundle is plain data (no functions), which means a Server Component can import it and pass it to the widget as a prop.

The translations were not all written by native speakers. Corrections are welcome; see [Contributing a translation](#contributing-a-translation).

## Choosing the language

The `locale` prop takes one bundle or an array.

**One bundle** is always used, regardless of the page or browser:

```tsx
import { FeedbackProvider } from "pinpoint-feedback/nextjs";
import de from "pinpoint-feedback/locales/de";

<FeedbackProvider locale={de} />
```

**An array** lets the widget pick the best match for the page:

```tsx
import de from "pinpoint-feedback/locales/de";
import fr from "pinpoint-feedback/locales/fr";

<FeedbackProvider locale={[de, fr]} />
```

Negotiation:

1. Candidates, in order: `<html lang>`, then `navigator.languages` (or `navigator.language`).
2. For each candidate, an exact tag match wins (case-insensitive), then a match on the language part: `de-AT` → `de`, `pt` → `pt-BR`.
3. English is always available, whether or not you include it, and is the final fallback.

Because `<html lang>` comes first, a page marked `lang="en"` gets the English widget even for visitors whose browser prefers German. That keeps the widget in the page's language. Multi-language sites should set `<html lang>` per request (the [example app](../examples/nextjs-app) does this from `?lang=` and `Accept-Language`) or pass the matching single bundle.

Without `locale`, the widget is English. Keys missing from a bundle fall back to the English text.

`negotiateLocale(available, requested, fallback?)` and `detectPreferredLocales()` are exported from `pinpoint-feedback` if you want the same logic elsewhere.

## Overriding texts

`messages` overrides individual texts of the active language. It is a partial bundle with the sections `widget`, `editor`, `capture` and `report`; keys are type-checked, so typos fail the build.

```tsx
<FeedbackProvider
  locale={de}
  messages={{
    widget: { "launcher.label": "Hilfe", "dialog.title": "Problem melden" },
    editor: { "pin.added": "Markierung {number} gesetzt" },
  }}
/>
```

Overrides apply to whichever language was selected. With an array of bundles, pass per-language overrides yourself (the example app keys them by `bundle.locale`). Unknown keys are ignored.

`buttonLabel` also overrides `launcher.label`.

The full list of keys and their English texts is in [`packages/core/src/i18n`](../packages/core/src/i18n):

| Section | File | Used for |
| --- | --- | --- |
| `widget` | `widget.ts` | Button, dialog, form, toolbar, errors, progress. |
| `editor` | `editor.ts` | Annotation editor labels and screen-reader announcements. |
| `capture` | `capture.ts` | Placeholder labels drawn into screenshots and capture warnings shown in the widget. |
| `report` | `report.ts` | Notion page body (server side). |

## Message format

A message is either a string or a plural object.

**Strings** use `{name}` placeholders. Keep every placeholder of the English text; numeric values are formatted with `Intl.NumberFormat` for the active language. Unknown placeholders are left as-is.

```ts
"toolbar.zoomReset": "Reset zoom to {percent}"
```

**Plural objects** are keyed by [CLDR plural category](https://cldr.unicode.org/index/cldr-spec/plural-rules) (`zero`, `one`, `two`, `few`, `many`, `other`). `other` is required. `#` is replaced by the formatted `count`; `{name}` placeholders work too. The category is chosen with `Intl.PluralRules` for the active language.

```ts
"launcher.labelWithPending": {
  one: "{label}, # unsent report",
  other: "{label}, # unsent reports",
}
```

Languages without plural forms only need `other`. Percentages and lists are formatted with `Intl` as well. Keyboard shortcut labels (⌘, Ctrl, Esc) are not translated.

## Your own language

Build a complete bundle with `defineLocale` from the root entry. It type-checks that every key of every section is present with the right kind (string or plural object). Starting from an existing bundle is easiest:

```ts
// locales/sv.ts
import { defineLocale } from "pinpoint-feedback";
import en from "pinpoint-feedback/locales/en";

export const sv = defineLocale({
  ...en,
  locale: "sv",
  dir: "ltr",
  widget: { ...en.widget, "launcher.label": "Återkoppling", "dialog.title": "Skicka återkoppling" /* … */ },
  editor: { ...en.editor /* … */ },
  capture: { ...en.capture /* … */ },
  report: { ...en.report /* … */ },
});
```

Pass it like a built-in bundle (`locale={sv}` or in an array). A bundle has:

| Field | Type | Description |
| --- | --- | --- |
| `locale` | `string` | BCP 47 tag. Used for negotiation and for `Intl` formatting and plural rules. |
| `dir` | `"ltr" \| "rtl"` | Text direction of the widget. |
| `widget`, `editor`, `capture`, `report` | message maps | See [Overriding texts](#overriding-texts). |

## Category labels

A category's `label` is what Notion stores, so it is the same in every language. Give the widget translated labels with `labels`, keyed by language tag:

```ts
defineCategories([
  "bug",
  { id: "perf", label: "Performance", labels: { de: "Leistung", fr: "Performances", "pt-BR": "Desempenho" } },
]);
```

Lookup: exact tag, then the language part (`de-AT` → `de`), then `label`.

Built-in categories (`"bug"`, `"design"`, …) are translated by the locale bundle as long as their label is unchanged. Priority names are translated in the widget; Notion keeps its fixed `Low` … `Critical` options. See [Categories](categories.md).

## Right-to-left

Bundles with `dir: "rtl"` (Arabic) switch the widget to right-to-left:

- The widget sets `lang` and `dir` on its own root inside the Shadow DOM; the page's `dir` is not changed or required.
- Layout uses logical CSS properties, so it mirrors: the form sits left of the screenshot, toolbar order and paddings flip, and directional icons (undo, redo, external link) are mirrored.
- The screenshot and the annotations on it are **never** mirrored. The editor canvas is always left-to-right; text annotations and pin notes use `dir="auto"`.
- The floating button stays in the corner chosen with `position`. Corners refer to the viewport, not reading direction.
- URLs in the form are always shown left-to-right.

## Notion report language

The Notion page body is written by the server, so its language is set on the handler and is independent of the widget's language:

```ts
// app/api/feedback/route.ts
import { createFeedbackHandler } from "pinpoint-feedback/nextjs/server";
import de from "pinpoint-feedback/locales/de";
import { categories } from "../../../feedback.config";

export const POST = createFeedbackHandler({ categories, locale: de });
```

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `locale` | `LocaleBundle` | English | Only its `report` section is used. |
| `messages` | `LocaleOverrides` | – | Overrides on top of `locale`; only `report` is used. |

`notion.locale` / `notion.messages` override these for the Notion backend only.

Localized: headings, callout, captions, field labels, pin and shape summaries, dates and numbers, capture notes. Capture warnings travel as codes with counts and are rendered in the report language, not the reporter's.

Never localized:

- Database property names (`Title`, `Status`, `Category`, `Priority`, …) and select options (`New`, `Low` … `Critical`, category labels). Filters and views keep working across languages.
- API error messages returned by the server. The widget shows its own translated text for every known error code.
- Server log output.

## Contributing a translation

1. Add `packages/core/src/locales/<tag>.ts`, following [`de.ts`](../packages/core/src/locales/de.ts) or another existing file:

   ```ts
   import { defineLocale } from "../i18n/bundle";

   export const ptBR = defineLocale({
     locale: "pt-BR",
     dir: "ltr",
     widget: { /* every key of en.widget */ },
     editor: { /* … */ },
     capture: { /* … */ },
     report: { /* … */ },
   });

   export default ptBR;
   ```

2. The build picks up every file in that folder and publishes it as `pinpoint-feedback/locales/<tag>`.
3. Run `npm test`. [`packages/core/test/locales.test.ts`](../packages/core/test/locales.test.ts) checks every bundle:
   - default export plus a named export equal to the camel-cased tag (`pt-BR` → `ptBR`);
   - `bundle.locale` equals the file name, and `Intl.PluralRules` accepts it;
   - `dir` is `"rtl"` for `ar`, `he`, `fa`, `ur` and `"ltr"` otherwise;
   - each section has exactly the English keys, with the same kind (string or plural object) and the same `{placeholders}`;
   - strings are not empty, plural objects have `other` and use only CLDR categories.
4. Add the language to the table above.

Translations should be reviewed by a native speaker before release. They are plain TypeScript objects, so corrections are an ordinary pull request.
